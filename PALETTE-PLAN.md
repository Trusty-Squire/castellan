# Plan: UI Primitive Palette → close cheap-model e2e

## Context & evidence (this session)
- **Single-piece-flow validated.** Splitting the bundled `secure-storage` node into
  `crypto → auth → storage` (each a KNOWN module interface) made all three pass on cheap
  models — `auth` on qwen's first try. Variance collapsed.
- **Free-form UI is the residual wall.** The `web-app` node fails repeatedly with the SAME
  signature (`Cannot GET /login.html`): the cheap model serves the login surface at an
  improvised route/file/testid layout, and the DOM gate has to GUESS it. ~13 builds of
  URL/file/route guessing were the single cost of an *improvised contract*, not 13 bugs.
- **Research verdict (16 sources, adversarial):** constraining LLM UI to a fixed palette of
  pre-built primitives makes the UI contract predetermined by humans → the determinism a
  deterministic gate needs; pre-built components expose stable hooks (roles/labels) so the gate
  targets them without guessing. Refuted: "free-form custom UI works reliably."

## Principle
**Known contract beats guessed contract.** Backend got known contracts via decomposition;
the frontend gets them via a palette. In both, the cheap model composes against a *fixed,
known* contract instead of improvising one the gate must reverse-engineer.

## Design

### 1. The palette (vendored, pre-built, tested primitives)
A tiny library shipped INTO the build (not generated by the model). Each primitive exposes a
fixed contract: **{serving route, stable testid(s), data-binding shape}**. MVP (auth dashboard):

| Primitive | Route (fixed) | testids (fixed) | Data shape |
|---|---|---|---|
| `login-form` | `GET /` | login-form, email-input, password-input, login-button | posts `{email,password}` to `POST /login` |
| `dashboard-shell` | `GET /dashboard` (session-gated, else 302 `/`) | dashboard, logout-button | wraps one content widget |
| `keys-list` (widget) | mounted in dashboard | api-keys-list | `{[provider]: maskedKey}` |

Future widgets (swappable, same slot): `pie`, `trend`, `table` — each a fixed testid + data shape.

### 2. Composition model (model writes GLUE, not UI)
Two strategies considered:
- **(A) Vendored templates + glue (MVP).** Ship `login.html`, `dashboard.html` (fixed testids)
  as templates. The cheap model writes ONLY `app.js`: the routes (`GET /`, `POST /login`,
  `GET /dashboard`, `POST /logout`, `GET /api/keys`) and the data binding (validate via
  `storage.get_user_keys`, render the keys map into the dashboard template). DOM contract is
  FIXED (vendored); only server glue is free-form.
- **(B) Composition spec + runtime.** Model emits JSON (which primitives, bindings, routes); a
  vendored runtime renders. More deterministic, but requires building/maintaining a runtime.

**Choose (A) for the MVP** — minimal harness, no new runtime; the free-form residue (server
glue) is small and gated FUNCTIONALLY (HTTP), which is robust, unlike DOM-presence.

### 3. The gate (now deterministic)
Because routes + testids are FIXED by the palette:
- **DOM gate, no probe:** `GET /` → assert login-form testids (present because the template is
  vendored) → fill → submit → `/dashboard` → assert dashboard testids.
- **Functional glue gate (HTTP, robust):** seed a user; `POST /login` → cookie; `GET /dashboard`
  with cookie contains the keys; `GET /api/keys` (Basic Auth) returns the JSON; unauth
  `GET /dashboard` → 302. (Replaces brittle DOM-URL guessing with the precise HTTP contract.)

### 4. Funnel integration
- A `UI-surface → palette-primitive` mapping in derive: when a requirement matches a palette
  primitive (login, dashboard, list/chart), spec it as a COMPOSITION over the palette (vendor
  the templates into the node, brief = "wire these routes + bindings") and emit the deterministic
  gate from the palette's known contract.
- **Escape hatch:** surfaces not in the palette fall back to free-form + the (brittle) DOM-probe
  gate. The palette raises the FLOOR for common surfaces; it does not forbid bespoke UIs.

### 5. Closing the e2e goal
Re-spec `web-app` as a palette-composition node → re-run cheap-only mission. If `web-app`
passes (cheap model wires known primitives), then `bot-core` + `integration` (already HTTP-gated)
→ **full e2e on cheap models alone.**

## Milestones
- **M1** — vendor the 3 MVP primitives (`login.html`, `dashboard.html`, `keys-list` partial) with
  fixed testids + a documented serving contract; a deterministic DOM+functional gate derived from
  that contract.
- **M2** — re-spec the `web-app` node: brief = "serve these vendored templates at these routes,
  bind `storage.get_user_keys`"; blast_radius = `app.js` + the templates (read-only).
- **M3** — re-run cheap-only mission; web-app must pass on qwen/deepseek; confirm e2e.
- **M4** — generalize in derive: `looksLikeUi` → palette mapping + escape hatch; the swap model
  (`keys-list` → `pie`/`trend`) as a config choice.
- **M5** — measure: cheap-model pass-rate + gate-flakiness, free-form vs palette, over N runs
  (the dogfood experiment the research said is missing).

## Risks / open questions
- **Glue still free-form.** Server routes/bindings are model-written; relies on the functional
  HTTP gate being robust (it is — exact routes), but the model can still mis-bind. Mitigation:
  the functional gate + completeness nudge.
- **Palette coverage.** Only apps composable from the palette benefit; the long-tail hobby dev
  may want surfaces outside it. Escape hatch needed; measure coverage.
- **Vendoring mechanics.** How do templates enter the node's workdir read-only (a `.squire/`
  asset drop? a context file the model must serve verbatim?) without the model mangling them.
- **Over-constraint.** Does fixing testids/routes hurt when the user wants a different layout?
  Palette = floor, not ceiling.
- **Maintenance.** Someone maintains the palette as frameworks shift (research: fast-moving space).

## Success criteria
1. `web-app` passes on a cheap model (qwen/deepseek), knight disabled, with the deterministic gate.
2. Full cheap-only mission completes e2e (all nodes pass).
3. Gate-flakiness on the UI node drops materially vs free-form (M5 measurement).

## REVIEW OUTCOME (5-lens engineering panel, 2026-06-22) → REVISE-FIRST

The diagnosis (free-form UI is the wall; known contract beats guessed) is right, but the plan
as written has blockers and is mis-sequenced. Key findings (all verified against the code):

- **BLOCKER — the read-only template vendoring has no home.** `.squire/` is the only injection
  path and it's git-excluded (can't be served); `resetTo()` runs `git reset --hard` + `git clean
  -fdq` every rung, so untracked vendored files are WIPED; blast_radius is allow-list-only (no
  DENY). Fix: commit templates into the git BASELINE (so `reset --hard` restores them) and make
  them read-only by OMITTING from blast_radius. Test ≥2-rung survival.
- **BLOCKER — `briefFileCoherence` silently reverses the read-only intent**: it auto-widens the
  radius to `**/login.html` for any brief-named file, re-granting write to the frozen template.
  Needs an explicit carve-out / a "SERVE the vendored X" phrasing that misses `BRIEF_CREATE_RE`.
- **BLOCKER — DOM-presence on vendored hooks is TRUE BY CONSTRUCTION** = the clairvoyance
  vacuous-pass: a static 200 of the unmodified template passes green on a totally broken app.
  The gate must be CONTENT-BINDING (seed a random sentinel key → assert `GET /api/keys` returns
  THAT exact value → plaintext-absent if masked → unauth `GET /dashboard` → 302), specified as a
  concrete anti-gaming command, run through `gateProofread`/`idempotencyRepair`, with a
  broken-app control.
- **The determinism win is partly ILLUSORY.** The palette fixes routes the GATE reads, not the
  routes the MODEL serves (it still writes app.js's route table). Vendoring template *content*
  doesn't constrain the Express routes → either `gotoAny` stays (not "deterministic") or you
  vendor the SERVER SKELETON, not the templates.
- **`deriveUiGate` already does ~80% of the proposed gate** — the palette should DELETE the
  `gotoAny` probe + method-name guessing (a simplification), not stand up a parallel UI-gate path.
- **Self-confirming-win risk:** the MVP palette IS the trustysquire auth-dashboard ser has
  dogfooded for weeks — passing M3 proves little about the real target (notes, trackers, games).

### OWNER REFRAME (2026-06-22) → primitives = AVAILABILITY, not a gate contract
"I don't know if you need to gate around the frontend primitives, just make it available to the
model as it builds. The cheap http gate seems like a good sanity check. Lift the floor but don't
get in its way."

This supersedes the heavy approach below. The palette is a RESOURCE the model reaches for (a
good, accessible component library in the build context), NOT a frozen contract the harness gates
against. This dissolves ALL THREE review blockers (read-only vendoring, briefFileCoherence
collision, content-binding DOM machinery) — they were artifacts of gating-against-fixed-primitives.

**The light plan (this is the plan):**
1. **Floor-lift — make good UI primitives AVAILABLE** in the UI node's context (accessible,
   decent-looking building blocks the model uses; shadcn-style). No vendoring substrate, no
   read-only enforcement, no gate machinery. The model writes its own files using good parts.
2. **HTTP functional sanity gate, with a SENTINEL** (deterministic, robust, no Chrome): seed a
   derive-time-random sentinel key → `POST /login` → cookie → `GET /api/keys` returns THAT exact
   value → masked (raw absent) → unauth `GET /dashboard` → 302 → cross-user isolation. The
   sentinel makes this more than a smoke test — it proves the DATA flows end-to-end, killing the
   "fake data" half of the clairvoyance failure. Through `gateProofread`/`idempotencyRepair`;
   broken-app control (hardcoded `/api/keys`, missing masking MUST fail).
3. **Keep the existing abstaining visual judge** for rendering quality / gross defects — it
   ABSTAINS on aesthetics and routes to the human (the thesis's final gate). Do NOT add a
   deterministic content-binding DOM gate — that is "getting in the way."

Layering: floor-lift (good parts) + functional sanity (data provably flows) + abstaining visual
+ human final gate. The objective gate verifies the thing FUNCTIONS; it does not verify pixels.

### (SUPERSEDED) earlier REVISED SEQUENCING — kept for the record
- **STEP 0 — re-baseline the evidence.** Instrument the ~13 web-app failures: how many failed
  because the GATE couldn't find the surface vs the MODEL never served a working app? This
  decides whether the plan even aims at the real wall (the panel suspects model-never-served
  dominates → gate-determinism doesn't help that; only a server skeleton does).
- **STEP 1 — pin routes in CONTRACT_FIRST** (`GET /`, `GET /dashboard`; the contract already
  pins port + start command). `planLoginFlow` prefers the pinned route over `gotoAny`. ~10 lines,
  no new primitive, no git-clean/blast-radius/coherence hazard.
- **STEP 2 — gate BOTH surfaces, each at its own layer. (Owner correction: an HTTP-only gate
  makes the gate passable but does NOT gate the frontend — a blank `dashboard.html` would pass.
  The deliverable IS the rendered UI; verifying it requires the browser. Do not demote the DOM
  gate — make it CONTENT-BINDING.)**
  - **Frontend gate (necessary, browser-driven, content-binding):** seed a user whose key is a
    derive-time RANDOM sentinel; log in; load `/dashboard`; assert `[data-testid=api-keys-list]`
    **`includes`** the sentinel (masked) — not just `exists`. The dom-gate already has the
    `includes` op; `deriveUiGate` uses only `exists:true` (derive2.ts:490) — that one-line change
    kills the vacuous-pass AND verifies the user actually sees their data. Also assert the login
    form renders + submit redirects + logout clears session.
  - **Agent-API gate (complement, HTTP):** `GET /api/keys` (Basic Auth) returns the exact
    sentinel, raw key absent if masked, unauth `GET /dashboard` → 302, cross-user isolation. This
    covers the SEPARATE agent-facing surface in the brief — it never stands in for the UI gate.
  - Both through `gateProofread`/`idempotencyRepair`; add a broken-app control (blank dashboard,
    hardcoded `/api/keys`, missing masking MUST all fail).
  - Route-pinning (STEP 1) + the server skeleton (STEP 3) exist to make the CONTENT-BINDING DOM
    gate deterministic — NOT to avoid it.
- **STEPS 1–2 test "known contract beats guessed" on ONE node with NO new harness primitive.**
  Only if that arm STILL fails cheap-model e2e →
- **STEP 3 — vendor the SERVER SKELETON** (route table + session middleware), model fills ONLY
  the `storage.get_user_keys → {provider: maskedKey}` data-binding callback. "A fixed Express
  skeleton with one injection point is not a runtime — it's a vendored file with a TODO." This is
  the only version that collapses server-verb variance to single-piece-flow level. Design the
  read-only substrate here (commit-to-baseline + omit-from-radius + `briefFileCoherence`
  carve-out + integrity grep + ≥2-rung survival test).
- **STEP 4 — prove cheap-model pass** with session/302 isolated as a sub-check.
- **STEP 5 — measure** (broken-app control; hold the artifact CONSTANT across arms, vary only
  contract-determinism).
- **STEP 6 (last) — generalize in derive** as a deterministic `paletteCoherence` post-pass next
  to `portCoherence`/`toolingCoherence` (NOT decompose-prompt prose — domain hints get removed as
  overfit), with `looksLikeUi` → free-form as the untouched escape hatch.

### The unforced error the panel flagged
Rejecting "vendor the server skeleton" (strategy B) as "needs a runtime" was wrong — a fixed
route table + session middleware with one data-binding injection point is just a vendored file,
and it's the ONLY variant that reduces the cheap model's degrees of freedom to the level that
made single-piece-flow reliable. The DOM-template vendoring pins the nouns; the server skeleton
pins the verbs — and the verbs (sessions, the 302 contract, cookie+Basic auth) are the cheap
model's PRIMARY failure mode, not a residual.
